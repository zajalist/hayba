## Root causes and minimal fixes

### 1. Generated build backups are incorrectly discovered as tests

Vitest excludes `**/dist/**` but backup folders match default test discovery: `dist.r11` (221 suites), `dist.r10ue59` (213), `dist.r9` (209), `dist.before-restart8` (204), `dist.old` (200). Old PIE tests already failed 17 assertions across five compiled suites, and five backup Python suites could not collect. These do not describe current source behavior.

Added `**/dist.*/**` to the isolated worktree's Vitest exclusions and `/mcp-tools/hayba-mcp/dist.*/` to root `.gitignore`. No directories deleted. CLI comparison preserved exactly all 295 baseline source suites (276 `src`, 18 `tests`, 1 `scripts`). Current worktree discovery has 296 suites because another agent added a source regression test. `git check-ignore` matches the backup path and does not match source or catalog test paths.

### 2. Catalog suite SyntaxError is a transformed shebang

Original catalog module passes `node --check` and direct Node import. Vite SSR transformation prepends export/import setup above the retained `#!/usr/bin/env node`, placing it on line 7 of transformed code (line 8 when wrapped for execution). The shebang is only valid as the first line. `vm.Script` reproduces the exact SyntaxError at that line; test module itself parses. Evidence: `probe-transform.log`, `skills-catalog.mjs.transformed.js`, `catalog-test.log`.

Removed the unused shebang. All repository callers/documentation invoke `node scripts/skills-catalog.mjs`; it is not a package bin. Existing six tests now execute and protect the import regression.

Collection exposed a second bug: Windows `core.autocrlf=true` checks out `catalog.json` with 1,290 CRLF lines, while generation emits LF. Semantic JSON content was identical. Both CLI validation and test compared raw strings. Normalized CRLF to LF at both comparison points. Added a CLI regression that accepts a CRLF catalog and then rejects changed catalog contents. Seven catalog tests pass; stale contents remain rejected.

### 3. SDK cold module loading consumes the request test's deadline

The first real OpenAI SDK import happens during the first `client.stream()` operation. In the baseline full run that test takes 5,713 ms and breaches the 5,000 ms deadline. Isolated original-source rerun passes all nine tests: first request 3,003 ms, subsequent complete/stream operations 5–11 ms. Direct Node SDK import alone measured 347 ms, which does not include the Vitest module-loader path.

Moved `await import('openai')` into existing `beforeAll`, after the external-request confinement guard. This keeps production lazy construction intact and separates fixture module loading from request behavior. No request or hook timeout increased. Focused upgraded-worktree runs show first request 43–53 ms and all nine tests passing. Dependency versions differ between original and fixed worktree; do not attribute the entire speed difference exclusively to the setup change without an identical-version benchmark.

### 4. Survival helper subprocess setup is load-sensitive; no source change

`src/tools/survival-raw-helpers.test.ts:14` starts PowerShell synchronously with a 10,000 ms process timeout. Its first group's setup exceeds that deadline in both the baseline and isolated Vitest run. This produces 12 skipped tests, not intentional capability skips. The second client-probe group passes all 20 tests. Isolated total: 20 passed / 12 skipped, failed suite, 53.40 seconds.

The helper parses PowerShell ASTs, loads exact helper definitions, compiles an Add-Type C# fixture, and exercises ephemeral loopback listeners. It does not call UE. A diagnostic direct subprocess run with a 60-second ceiling passed all 11 scenarios in 4.12 seconds with empty stderr (`survival-helpers-direct.json`). Scenario timing bounds all passed. This supports setup/load sensitivity, but does not isolate which setup phase exceeded 10 seconds in the failing run. Do not blindly increase the production test deadline. Recheck in the clean worktree and instrument startup / AST parsing / Add-Type if the failure persists.

## Follow-up: native transcript scaling (read-only)

The update path is throttled to once per 0.1 seconds (`HaybaMCPChatPanel.cpp:718`) and exits early unless dirty or flags changed (`HaybaMCPChatPresentation.cpp:87`). It is therefore not one serialization per token and does not serialize idle unchanged transcripts. Each accepted dirty update nevertheless rebuilds every message, every associated activity step and verdict, and the whole workspace (`HaybaMCPChatPresentation.cpp:100`). It invokes `FindActivity` even for empty message activity IDs; that lookup is a linear scan (`HaybaMCPActivityModel.cpp:156`). No activity count cap was found in that model.

`SHaybaChatTranscript.cpp:129` serializes the complete snapshot before comparing JSON equality, then sends the entire changed snapshot via ExecuteJavascript. The 80-row window in `Resources/Chat/chat.js:399` bounds DOM work only; it retains all messages for earlier/later navigation. Workspace history search and approval selection also consume the complete message array. Simply sending the last 80 would break requested history/navigation/approval behavior.

Synthetic payload proxy (ASCII text, 1 KiB per message, no activity content) measured 88,627 bytes for 80 messages, 1,108,427 bytes for 1,000, and 11,093,927 bytes for 10,000. At the existing maximum 10 Hz these correspond to approximately 0.89 / 11.08 / 110.94 MB of JSON text per second before bridge overhead. Node stringify medians were 0.29 / 2.92 / 22.59 ms. This is a payload-size / JS-serialization proxy, NOT a native UE or CEF performance measurement. Saved as `transcript-payload-proxy.jsonl`.

Recommendation: retain the existing dirty/throttle behavior for this patch. A safe incremental protocol needs full snapshots on generation change/readiness, message IDs/revisions, changed-row updates, and compatibility with history search, older pages, text selection, and approvals. That is a cross-layer change deserving native/CEF measurement and its own regressions, not an unverified last-80 truncation. A small independent improvement could skip FindActivity for empty IDs, but that does not solve whole-history serialization and has not been implemented or native-benchmarked here.
